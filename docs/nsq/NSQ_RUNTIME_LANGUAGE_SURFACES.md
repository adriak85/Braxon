# NSQ Runtime Language Surfaces

## Canon rule

Languages and dialects are built into the NSQ runtime as native runtime surfaces.

They are not plugins.

They are not hooks.

They are not wrappers.

They are not source-only lowering.

They are not foreign authority.

A language spelling can be projected into NSQ, but the native NSQ meaning remains sovereign.

A runtime language surface is valid only when it has:

- native surface identity
- native ingress rule
- canonical NSQ representation
- court route
- flag registry
- platform binding
- fail-closed availability state
- projection spelling only as compatibility, not authority

If a dialect is not enabled in current runtime sight, insertion fails closed.

Header-only insertion is lawful only when the runtime already sees the dialect and the enabled dialect set contains that surface.

## Native runtime interpretation

A language surface is not the language itself running as a foreign master.

A language surface is the NSQ-native court-readable representation of that language's callable structure, symbols, flags, build behavior, runtime behavior, package behavior, and platform effects.

Python is not authority.

Rust is not authority.

C is not authority.

ASM is not authority.

The runtime may use C or ASM for hot loops, but NSQ remains the authority.

The runtime may use Lisp-like structure for canonical symbolic transformation, but NSQ remains the authority.

The runtime may use Rust as the implementation host, but NSQ remains the authority.

## Platform integration

The runtime platform is part of the runtime surface.

Android/Termux/aarch64-linux-android is the primary current platform target.

The platform surface must include:

- target triple
- executable surface
- shell surface
- package manager surface
- filesystem roots
- storage policy
- graphics API
- build tools
- signing tools when Android packaging is active
- model installation policy
- fail-closed rule for missing tools

## Model integration

Model installation is runtime-managed through manifests, stamps, byte-count witnesses, full cryptographic hashes, and NSQ semantic digests.

The model lane must distinguish:

- source config
- tokenizer config
- transport source
- NSQ compressed artifact
- stamp bundle
- lazy-load parameter projection
- full byte identity proof
- NSQ semantic digest proof

A model is not installed merely because a pointer exists.

A model is installable when the registry, binding, source targets, and reconstruction manifest exist.

A model is installed when required local artifacts exist and their byte count plus full hashes match.

A model is hot-live only when runtime says it can execute or route through the local inference lane.
