# NSQASM Stamp Build Chain

Purpose:
- represent repeated code, framework blocks, functions, loops, syntax forms, and language projections as stamps
- keep stamps as wake/address/ignition triggers, not passive text and not full payloads
- allow human-readable input/output while preserving NSQ court authority
- prebake validated blocks before runtime projection to reduce overhead
- support a shared stamp database usable by Braxon and future projects

Court placement:
- Queen validates candidate stamps.
- Bishop prepares, imbues, elevates, recycles, or reassigns stamp material.
- King/composer performs final assembly and signs promoted build-chain output.

Build-chain order:
1. scan source or records for candidate reusable blocks
2. write candidate stamp records as untrusted/local
3. route candidates to Queen validation
4. route reusable/elevatable candidates to Bishop preparation
5. route final composed projection to King/composer
6. emit WakeDispatch-ready projection
7. currently project to binary/assembly/host language as filtered output
8. later project directly to complete NSQ/NSQASM when native coverage is ready

Rules:
- no passive stamp-only mode
- every accepted stamp must have stored operation or framework backing
- every accepted stamp must have wake packet behavior
- every accepted stamp must have materialization path
- every accepted stamp must preserve semantic execution continuity
- global stamp promotion requires court authority
- generated binaries are build outputs unless explicitly declared as golden fixtures
